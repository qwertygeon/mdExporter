## 1. 목표·요구사항

| # | 요구사항 | 비고 |
|---|---|---|
| R1 | 원본 markdown 의 **문구·내용을 변경하지 않는다** | 변환은 스타일 부여만 |
| R2 | **시인성**을 우선한다 (한글 문서 기준) | 폰트·줄폭·줄간격·표 가독성 |
| R3 | 디자인이 **세련되고 깔끔**해야 한다 | 액센트 컬러·콜아웃·코드 박스 |
| R4 | HTML 과 PDF **두 포맷을 동일 디자인**으로 산출한다 | 단일 CSS 소스 |
| R5 | 다른 문서에도 **재사용 가능한 테마**여야 한다 | 문서별 CSS 재작성 금지 |
| R6 | 설치·운영 부담이 낮아야 한다 | npx 단발 실행으로 동작 |

## 2. 도구 선정 분석

### 2-1. 후보 비교

| 후보 | 평가 | 결론 |
|---|---|---|
| **mdpress** | markdown 을 impress.js **슬라이드(프레젠테이션)** 로 변환하는 도구 | 문서 변환 목적에 부적합 — 제외 |
| **pandoc** | 구조 변환(포맷 간 상호 변환)은 최강. `--standalone` + 커스텀 template/CSS 로 HTML 은 대응 가능 | PDF 기본 경로가 LaTeX 엔진이라 한글 폰트·CSS 기반 디자인 통제에 불리 — 제외 |
| **Chromium 인쇄 계열 (md-to-pdf)** | HTML+CSS 를 브라우저 인쇄 그대로 PDF 화. 웹폰트·`@page` 여백·`break-inside` 페이지 나눔을 모두 CSS 로 제어 | **채택** |
| **완전 자체 구현** (파서 포함) | markdown 파싱·표·각주·코드 하이라이트 등 엣지 케이스를 재발명하게 됨. 디자인 품질에는 기여 없음 | 제외 — 파싱은 기존 파서 사용이 원칙 |

### 2-2. 결정: md-to-pdf + 자체 CSS 테마

핵심 판단: **문서의 시인성·세련됨은 변환기가 아니라 CSS/템플릿에서 나온다.**
Markdown→HTML 변환 결과 구조는 어떤 도구든 거의 같으므로, 변환기는 검증된 기존 도구를 쓰고 투자와 통제는 테마(CSS)에 집중한다.

- 채택 도구: [`md-to-pdf`](https://github.com/simonhaenisch/md-to-pdf) — 검증 시점 사용 버전 5.2.5. 내부적으로 markdown 파싱 후 headless Chromium(puppeteer) 인쇄로 PDF 를 생성한다.
- 실행 방식: `npx --yes md-to-pdf` — 전역 설치 없이 단발 실행 (R6).
- 디자인: 자체 `theme.css` 한 벌 (R2·R3·R5). `--stylesheet` 옵션으로 주입한다.
- HTML 산출: 같은 도구의 `--as-html` 옵션 사용 (R4 — 동일 파서·동일 CSS 보장).

## 3. 아키텍처 — 변환 파이프라인

```
대상문서.md ──┬── md-to-pdf --stylesheet theme.css --pdf-options {...} ──→ 대상문서.pdf
              │      (markdown 파싱 → HTML → Chromium 인쇄)
              │
              └── md-to-pdf --as-html --stylesheet theme.css ──→ 대상문서.html
                                                                      │
                                            perl 후처리 (<title> 주입) ┘
```

구성 요소:

| 구성 요소 | 역할 |
|---|---|
| `theme.css` | 디자인 SSOT. 타이포그래피·헤딩·표·코드·콜아웃·인쇄 규칙 전부 보유 |
| `--pdf-options` (JSON) | 페이지 포맷(A4)·여백(상하 18mm, 좌우 15mm)·`printBackground: true` |
| `<title>` 후처리 | HTML 산출물의 빈 `<title>` 을 문서 제목으로 치환 (근거: [§5](#5-알려진-제약)) |

## 4. 설계 결정 (ADR)

| ID | 결정 | 이유 |
|---|---|---|
| ADR-1 | 파서를 직접 구현하지 않는다 | 표·각주·중첩 목록·코드펜스 등 엣지 케이스는 기존 파서가 이미 해결. 재발명은 디자인 품질에 기여하지 않음 |
| ADR-2 | PDF 는 Chromium 인쇄 방식으로 생성한다 | 단일 CSS 로 HTML/PDF 디자인 일치(R4). 웹폰트·페이지 제어를 CSS 표준(`@media print`·`break-inside`)으로 해결 |
| ADR-3 | `theme.css` 는 완결적(self-contained)으로 작성한다 | 도구 기본 스타일에 의존하면 도구 버전·옵션에 따라 결과가 흔들림. 모든 요소(body·헤딩·표·코드·인용)를 자체 정의 |
| ADR-4 | 한글 폰트는 Pretendard 웹폰트 + 시스템 폰트 폴백 | 현장·PC 별 설치 폰트 편차를 웹폰트로 흡수하고, 오프라인 시 Apple SD Gothic Neo/Noto Sans KR 로 폴백 |
| ADR-5 | 실행은 npx 단발 호출 | 전역 설치·버전 관리 부담 제거(R6). 재현 커맨드가 문서 한 줄로 고정됨 |

## 5. 알려진 제약

- **웹폰트는 네트워크 필요**: Pretendard 를 CDN(jsdelivr)에서 로드하므로 오프라인 변환 시 폴백 시스템 폰트로 렌더링된다. 오프라인 고정이 필요하면 폰트 파일을 로컬 동봉하고 `@font-face` 로 교체한다.
- **HTML `<title>` 이 비어 있음**: md-to-pdf 5.2.5 의 `--as-html` 산출물은 `<title></title>` 로 생성된다(실측). 후처리로 문서 제목을 주입한다.
- **최초 실행 비용**: npx 가 md-to-pdf 와 Chromium 을 내려받으므로 최초 1회는 수 분이 걸릴 수 있다. 이후 캐시로 수 초 내 완료.
- **PDF 시각 검증 자동화 부재**: 렌더링 결과 확인은 사람 눈 검수 기준이다. 자동화하려면 poppler(`pdftoppm`) 등 렌더러 설치가 필요하다.

## 6. 로드맵 — 자체 도구 승격 (2단계)

반복 사용·팀 표준 테마 요구가 생기면 얇은 자체 스크립트로 승격한다. 승격 후에도 markdown 파싱은 기존 파서를 쓴다(ADR-1 유지).

| 항목 | 내용 |
|---|---|
| 구성 | markdown-it(파싱) + 자체 HTML 템플릿 + Playwright(브라우저 인쇄) |
| 규모 | 100줄 내외의 단일 스크립트 |
| 승격 트리거 | md-to-pdf 로 불가능한 커스텀이 필요해질 때 |
| 확보 기능 | 목차(TOC) 자동 생성, 표지 페이지, 헤더/푸터(페이지 번호·문서명), 다중 문서 일괄 변환 |
| 유지 사항 | `theme.css` 를 그대로 계승 (디자인 SSOT 불변), HTML/PDF 동일 소스 원칙(R4) |
